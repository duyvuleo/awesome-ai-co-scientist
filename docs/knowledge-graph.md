# Evidence graph pilot

[Open the pilot](https://duyvuleo.github.io/awesome-ai-co-scientist/knowledge-graph/) · [Generated evidence answers](knowledge-graph-evidence.md) · [Collection explorer](https://duyvuleo.github.io/awesome-ai-co-scientist/)

The pilot connects scoped assertions to source passages, pinned artifacts, evaluation configurations, and review history. It covers ScienceCUA/ScienceBoard, Continual AutoResearch, Cloudra, and two existing local component reports. It is separate from the collection’s theme explorer.

## Five reader questions

| Question | Evidence to retain |
| --- | --- |
| Does the inspected ScienceCUA release contain the full evaluated method? | Paper-described capability and available software components. |
| Can ScienceBoard scores be compared directly across revisions? | Task inventories, repairs, split roles, and source versions. |
| Does persistent research state improve the final result? | Initialization, subsequent search, and final selection under matched conditions. |
| Where does human work enter Cloudra’s evaluation? | Offline record reconstruction, runtime delivery, and calculation evidence. |
| What has this collection actually reproduced? | The exact executed component, source pin, original date, and untested claims. |

Choose a question, then inspect an assertion in the table or cards. Its neighborhood graph displays only declared relationships and source support. The details retain source locators, evidence scope, reviewer role, and evaluation conditions. Labels remain visible. The table provides the same information without relying on the graph.

Answers are assembled from eligible statements, not generated by a model. Missing evidence returns **not established in the inspected sources**. A source change can withhold an affected statement pending another review. Shared themes and citations do not create support, derivation, or contradiction edges.

## Data model

| Record | Purpose |
| --- | --- |
| Objects | Distinct papers, implementations, methods, benchmark versions, outcomes, and scopes. Catalog IDs provide navigation; grouped reading nodes do not merge graph identities. |
| Sources and evidence | Pinned source URL, publication/inspection dates, exact locator, evidence basis, stance, and scope. Existing execution records retain their original execution dates and file hashes. |
| Configurations and evaluations | Model/scaffold, inputs, benchmark version, split, metric, aggregation, budget, human role, protocol, and outcome context. Unknown values carry explicit reasons. |
| Statement revisions | Stable claim ID, immutable revision ID, typed endpoints, assertion text, scope, evidence references, evaluation references, and predecessor. |
| Reviews | Actual reviewer role, decision, timestamp, and reason. An assistant review is not recorded as human verification. |
| Source events | A revision, correction, withdrawal, or availability change that flags affected statements. A withdrawal does not automatically prove every assertion false. |

The canonical data is [pilot.json](../data/knowledge-graph/pilot.json); [schema.json](../data/knowledge-graph/schema.json) describes its structure. Both are also [published with the pilot](https://duyvuleo.github.io/awesome-ai-co-scientist/knowledge-graph/pilot.json), including the [schema](https://duyvuleo.github.io/awesome-ai-co-scientist/knowledge-graph/schema.json). The Python validator supports the schema’s declared keyword profile and checks graph semantics, pins, references, chronology, and local report hashes. It is not a general JSON Schema engine. A full draft-2020-12 validator can also consume the schema.

Review state, evidence stance, and lifecycle remain separate. Current answers use accepted revisions with clear source-review status. Candidate or deferred revisions do not replace an accepted revision. A retraction removes that revision from current answers without reviving an older superseded revision. History remains available.

The pilot uses structural predicates: `describes`, `implements`, `planned_component`, `revises`, `includes`, `has_observation`, `evaluated_on`, `uses`, `reports`, `has_human_role`, `has_scope`, and `untested_scope`. Endpoint types are enforced. Scientific support is qualified by an evidence record; it is never inferred transitively. Introducing new relation meanings requires a deliberate schema and evidence-policy change.

## Offline queries

Commands use only local data and Python’s standard library. Global options precede the command.

```bash
python3 scripts/knowledge_graph.py questions
python3 scripts/knowledge_graph.py answer release-scope
python3 scripts/knowledge_graph.py --format json answer memory-outcomes
python3 scripts/knowledge_graph.py statements --family sciencecua
python3 scripts/knowledge_graph.py statements --predicate planned_component
python3 scripts/knowledge_graph.py history sc-code-construction
python3 scripts/knowledge_graph.py statements --as-of 2026-11-05
python3 scripts/knowledge_graph.py compare eval-sc-model eval-sc-native
python3 scripts/knowledge_graph.py impact src-sc-paper
python3 scripts/knowledge_graph.py review-queue
python3 scripts/knowledge_graph.py export-jsonld
```

`--as-of` accepts a UTC timestamp or a date interpreted through 23:59:59 UTC. It reconstructs the collection’s recorded assertions and review decisions, not the time when a scientific statement became true. Dates before the initial pilot return no accepted statements.

`compare` flags differences and missing values across declared evaluation fields. Matching context does not establish causal equivalence or rank systems. The tool does not infer independent replication from repeated reports or source versions.

## Append-only growth

Add objects, sources, evidence, statements, reviews, and source events with new IDs. Revise a claim by appending its next numbered revision and linking `supersedes` to its immediate predecessor. Preserve earlier records. An accepted review activates the revision; a pending revision leaves the earlier accepted record in place.

An update file contains a new `release` record and arrays of records to append. Validate it into a new candidate file:

```bash
python3 scripts/knowledge_graph.py apply .local/graph-update.json --output .local/graph-candidate.json
python3 scripts/knowledge_graph.py --data .local/graph-candidate.json validate --previous data/knowledge-graph/pilot.json
python3 scripts/knowledge_graph.py --data .local/graph-candidate.json diff data/knowledge-graph/pilot.json
```

The apply command refuses an existing output file and rejects modifications to existing records. Review the candidate before replacing canonical data. A source event flags current assertions that cite the source directly or through an evaluation; a later review records the decision. A review at the same timestamp as the source event does not clear it.

GitHub validation compares the proposed dataset with the push or pull-request base and rejects edits or deletion of existing graph records. This checks history preservation, not factual support. Factual review remains necessary. Routine catalog curation does not authorize new graph claims or relation-policy changes automatically.

Completed files under `reports/reproducibility/` remain dated execution records. The pilot indexes them without rerunning components, refreshing their dates, changing their outcomes, or spending model/API budget.

## Build and verify

```bash
python3 scripts/knowledge_graph.py validate
python3 scripts/render.py
python3 scripts/render.py --check
python3 scripts/validate.py
python3 -m unittest discover -s tests -v
node --test tests/*.test.mjs
python3 -m http.server 8768 --bind 127.0.0.1 --directory site
```

Open `http://127.0.0.1:8768/knowledge-graph/`. The existing renderer generates the public payload, qualified JSON-LD export, and evidence answers. The existing Pages workflow publishes the separate directory. No graph database, model service, CDN, or new frontend dependency is required.

JSON-LD reifies each assertion as an `rdf:Statement` with provenance and scope. It does not assert an unqualified scientific triple or claim nanopublication conformance. Provenance follows the distinction between assertion and publication metadata in [nanopublications](https://nanopub.net/), with [PROV-O](https://www.w3.org/TR/prov-o/) revision concepts. The [ORKG requirements analysis](https://arxiv.org/html/2102.06021v1) motivates evaluating specific reader tasks separately from broad discovery.

The acceptance tests cover the five source-located answer sets, missing evidence, incompatible contexts, record-order invariance, candidate/accepted/retracted histories, source-change dependencies, non-mutating exports, preserved execution records, and prevention of inferred scientific links. These are software and data-contract checks. They do not establish community utility, extraction accuracy across the collection, or scientific-result reproduction.
